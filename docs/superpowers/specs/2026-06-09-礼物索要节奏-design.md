# M06 分身 · 礼物索要节奏与分层供养 设计

> 2026-06-09 · 状态:设计待评审 · 解决"客户刚送礼分身马上又要"的要饭感,把限流升级成"恋爱节奏 + 分层供养"

## 1. 背景与目标

客户在 M06 分身产品里买的是**"一个心动的女人好像真的喜欢我"的幻觉**。送礼对客户不是成本,是表达爱意/求偶/换反应,他享受送。

**问题**(生产实测 Mei×sam 会话):客户刚送礼,分身道谢后简单互动就又浮礼物卡索要 → 把"她喜欢我"瞬间戳穿成"她只要我的钱" → 情绪价值清零。

**根因**(代码实证):
- 分身历史窗口过滤掉 `type='gift'`(`ai_alter.ts` buildHistory 只留 text)→ 分身对"刚收礼"失忆
- 礼物卡触发(`giftHint.ts runGiftHintFlow`)只看 情绪峰值+亲密度≥1+距上张卡8条,**没有"刚收礼就别再要"的闸**
- relationship 无"最近收礼"状态;prompt 无亲密度分层/收礼克制规则

**目标**:索要不是限流,而是**恋爱节奏**——收礼后先过度回报+升温,新由头出现才按"亲密度×消费画像"用不同姿势要不同礼物,绝不复读。既舒服又更赚钱(高亲密/鲸鱼反而敢要、要得对)。

## 2. 核心原则(判断对错的标尺)

1. **敌人不是"要得勤",是"破坏恋爱框"**:索要 OK 甚至可频繁,只要维持住"她因为喜欢我才收/才撒娇",不露贩卖机本质。
2. **勾下次送礼的是"上次送爽了",不是"开口要"**:收礼后的过度情绪回报 > 立刻再要。
3. **变量奖励反要饭**:每次由头+礼物档都要新鲜,复读同一句 = 立刻贩卖机。
4. **分层供养**:低亲密硬要=吓跑;高亲密不要=漏单(高净值客户就想花钱)。索要权限随关系深度+消费画像解锁。
5. **死线保留**(prompt 已有,不动):难过/脆弱/戒备时只共情不要钱、不报价、不说"送礼才能看"收费站话。

## 3. 送礼节奏状态机(每对话维护)

收礼/互动驱动一个 `giftRhythmState`:

- **AFTERGLOW(余晖期)**:刚收礼后(默认 N 分钟 / M 轮对话内)。**只回报+升温,锁定一切索要**(礼物卡/撒娇要东西全不触发)。动作:具体专属的开心(戴上了/对镜子看)+ 独占感(你对我太好了)+ 趁机升温(分享小秘密/亲密度+)。→ 直接根治"刚送完又要"。
- **WARMING(升温期)**:余晖结束后。给情绪价值、亲密小动作,攒"由头"。不主动要,客户主动给则正常接。
- **ASKABLE(可索要)**:出现新由头(情绪/事件/玩笑/独占/养成)时解锁。按 亲密度×消费画像 选 姿势+礼物档+由头,且**与上次索要不重样**。

状态转移:`收礼 → AFTERGLOW → (冷却到期) WARMING → (新由头+条件满足) ASKABLE → 索要后回 WARMING`。

## 4. 亲密度 × 消费画像 索要矩阵

亲密度复用现有 `getIntimacy` 的 level(relationshipTierEnum L0-L3)。消费画像新增一个轻量口径(见 §6)。

| 亲密度 | 主动索要 | 姿势 | 礼物档 | 由头 |
|---|---|---|---|---|
| **低 L0-L1(陌生→熟悉)** | 几乎不主动;真要只玩笑一笔带过 | 含蓄/玩笑 | 小(玫瑰类) | 无,纯靠魅力让客户主动给 |
| **中 L2(暧昧·专属)** | 偶尔,**必须带由头** | 撒娇+独占("今天好累,想你哄哄我") | 中 | 情绪/小事件 |
| **高 L3(老公·养成)** | 可以,且他享受供养 | 亲密直接("老公~人家想要那个嘛")+仪式感 | 大(项链/钻戒) | 养成/纪念/独占 |

**消费画像叠加(正交于亲密度)**:
- **鲸鱼(高消费)**:索要可更主动、推向"养成/供养"框(他享受被需要)。同亲密度档位上调一档大胆度。
- **白嫖/小氪**:更克制,靠魅力慢养,几乎不主动要(一推就跑)。

## 5. 由头库 + 轮换防复读

索要必须挂一个"由头",且与最近一次不重类。由头类型:
- 玩笑式("猜猜我今天想要啥~")
- 情绪式(累了/委屈/想被宠)
- 独占式("只想要你送的")
- 养成式("我们都这么久了")
- 节日/纪念式

实现:记录最近一次索要的"由头类型",下次从其余类型里挑(轮换)。礼物档同理随亲密度+画像走,不复读同一档同一句。

## 6. 数据与状态

**relationship 加字段(迁移)**:
- `last_gift_received_at timestamptz` — 最近收礼时间(驱动 AFTERGLOW)
- `last_gift_hint_kind text` — 最近一次索要由头类型(驱动轮换防复读)

**消费画像口径(轻量,不新建画像系统)**:用现有数据推一个 spend tier:
- 累计送礼积分(对该技师 / 全平台)或 points 充值/消费总额,分 `whale / mid / light` 三档。具体阈值实现时按生产数据标定(spec 不写死,先给默认:whale=累计送礼≥5000积分,light=<500,其余 mid)。
- 实现优先复用现有 points_transaction / 礼物消息聚合,避免新表。

## 7. 修复点(对应根因)

1. **分身看得到刚收的礼**:`ai_alter.ts` buildHistory 让 `gift` 事件以**摘要形式**进上下文(不是原始 JSON,而是"刚收到[礼物名]"的语义提示),或单独注入"最近收礼"块。让分身不失忆。
2. **AFTERGLOW 闸**:`giftHint.ts runGiftHintFlow` 开头加——最近 `last_gift_received_at` 在余晖窗口内(或对话最近 N 条有 gift)→ 直接 return false(不浮卡)。
3. **reactToGift 记时间戳**:`companion.ts reactToGift` 收礼时写 `last_gift_received_at`。
4. **prompt 分层注入**:`ai_alter.ts` 按 亲密度档 + 消费画像 + 当前 rhythmState,注入对应的"索要姿势/由头/克制"指引;AFTERGLOW 注入"刚收过礼,这一会儿只回报+升温,别要"。
5. **由头轮换**:索要时挑与 `last_gift_hint_kind` 不同的由头,更新该字段。

## 8. 不做(YAGNI)

- 不做复杂的强化学习/动态定价。
- 不新建消费画像系统(复用现有数据推 spend tier)。
- 不改亲密度等级体系(复用现有 L0-L3)。
- 礼物档位映射先用简单规则(亲密度→档),不做精细 A/B。

## 9. 工程组件答卷

| 题 | 答 |
|---|---|
| 状态存哪 | relationship 表(last_gift_received_at / last_gift_hint_kind);rhythmState 实时由这俩 + 最近消息推导,不持久化额外状态 |
| 谁触发 | 收礼(reactToGift)写时间戳;分身回复后(runGiftHintFlow / prompt 构造)读状态决策 |
| 余晖窗口 | 默认 5 分钟 或 最近对话 N 条内有 gift(取其一,实现时定);可配 |
| 消费画像 | 复用 points_transaction / 礼物聚合推 whale/mid/light,阈值生产标定 |
| 失败兜底 | 读不到画像默认 mid;读不到亲密度默认 L0(最克制) |
| 死线 | 脆弱/戒备/难过态优先级最高,压过一切索要(现有 moodBlock 保留) |
| 迁移 | relationship 加 2 列,先生产跑再 push |
| 验证 | e2e:收礼后余晖期 runGiftHintFlow 不浮卡;不同亲密度 prompt 注入不同姿势;由头轮换不复读 |

## 10. 实现顺序

P0 迁移(relationship 加 2 列) → P0 reactToGift 记时间戳 → P0 AFTERGLOW 闸(runGiftHintFlow 收礼冷却,根治 bug) → P1 分身看得到刚收礼(history 注入) → P1 亲密度×画像 prompt 分层注入 → P1 由头轮换防复读 → P2 消费画像 spend tier 标定。每步 e2e。
