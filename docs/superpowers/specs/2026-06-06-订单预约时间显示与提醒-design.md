# 订单预约时间显示与两档提醒 — 设计文档

> 日期：2026-06-06
> 状态：设计已确认，待出实施计划

## 一、需求

进行中的订单需要让客户和技师都清楚地知道**预约时间**，并在临近赴约时主动提醒：

1. 订单列表（客户端 + 技师端）显示预约时间
2. 订单详情页（客户 + 技师）显示预约时间
3. 预约前**两档提醒**（1 小时 + 10 分钟），客户和技师都收到

## 三、已确认的设计决策

1. **提醒档位**：两档 —— 提前 1 小时 + 提前 10 分钟。
2. **提醒形式**：
   - 1 小时档：纯系统推送（站内 + Web Push）。
   - 10 分钟档：系统推送 **+** 技师 AI 分身发"快到啦"暖意消息。
3. **覆盖状态**：只提醒**已锁定时间、未开始**的订单（`LOCKED` / `PAID`）。`PENDING_CONFIRM` 时间未敲定不提醒，`IN_SERVICE` 已开始不提醒。
4. **详情页展示风格**：绝对时间 + 期待型倒计时（临近升温暖色仪式卡）。
5. **去重数据存法**：方案 A —— orders 表加两列（不另建表，贴合现有迁移模式，YAGNI）。

## 四、架构设计

### Part 1 — UI 显示预约时间（纯前端，不动 API）

**抽共享时间工具**：新建 `apps/web/lib/appointment-time.ts`，把 `OrderCard.tsx` 现成的三个函数提取为共享模块，供四个页面与 OrderCard 共用：

- `apptLocalDate(iso: string): Date` —— UTC ISO 的墙上分量当本地时间构造（O2O 同城精确）。
- `absLabel(date: Date): string` —— "今天 14:00 / 明天 14:00 / 周三 14:00"。
- `countdownLabel(date: Date, now: number): string | null` —— 期待型倒计时（分段递进、不跳秒、临近升温；无焦虑感）。

`OrderCard.tsx` 改为 import 该模块并删除本地副本（消除重复，单一真相源）。

**四处接入**：

| 页面 | 文件 | 展示内容 |
|---|---|---|
| 客户订单列表 | `app/order/page.tsx` | 卡片加一行绝对时间（📅 明天 14:00）。列表不放倒计时，避免焦虑。 |
| 技师订单列表 | `app/t/orders/page.tsx` | 同上。 |
| 客户订单详情 | `app/order/[id]/page.tsx` | 绝对时间 + 期待型倒计时块；临近 3h 升级为暖色仪式卡。 |
| 技师订单详情 | 技师订单详情视图（实现时确认路由：`app/t/orders/[id]` 或列表内展开） | 同客户详情。 |

> 接入只对 `scheduledAt` 非空的订单显示；为空时整块隐藏（不显示"待定"占位以免噪音，除非实现时发现需要）。

### Part 2 — 两档预约提醒 cron（核心缺口）

**数据层**：迁移给 orders 表加两列（timestamptz, nullable）：

- `reminder_1h_sent_at`
- `reminder_10m_sent_at`

迁移号顺延现有序列（实现时取下一个可用号，如 0041），先在生产跑迁移再 push（铁律：新列必先迁移防部署窗口报错）。

**新建 cron**：`apps/api/src/jobs/appointment-reminder.ts`，`setInterval` 每 2 分钟扫一次（卡准 10 分钟窗口，2 分钟间隔最大偏差可接受）。

逻辑：

```
扫 orders WHERE status IN ('LOCKED','PAID')
            AND scheduled_at IS NOT NULL
            AND scheduled_at 在未来
对每单：用 realEpoch() 还原技师本地真实时刻 → 计算 minutesUntil

  【1 小时档】 60 ≥ minutesUntil > 10  且  reminder_1h_sent_at IS NULL
    → enqueue 系统推送给【客户】+【技师】
    → UPDATE reminder_1h_sent_at = now()

  【10 分钟档】 10 ≥ minutesUntil > 0  且  reminder_10m_sent_at IS NULL
    → enqueue 系统推送给【客户】+【技师】
    → 触发技师分身发"快到啦"暖意消息
    → UPDATE reminder_10m_sent_at = now()
```

**推送内容**（复用 `notifications.enqueue()`）：

- level = `important`
- category = 新增 `appointment_reminder`（加入 notifications.ts 的 category 枚举与 `CATEGORY_PREF_KEY`）
- deepLink = `/order/:id`
- 客户文案："您预约的 {技师名} 还有 1 小时开始"（10 分钟档相应改文案）
- 技师文案："您与 {客户名} 的预约还有 1 小时"

**分身暖意消息**（仅 10 分钟档）：复用 `ai-alter-pre-appointment.ts` 的分身发消息机制。

**挂载**：在 `apps/api/src/jobs/index.ts` 的启动列表注册 `appointment-reminder`。

### 与现有 `ai-alter-pre-appointment` 的冲突处理

现有任务已在预约前 2.5h 内让分身发过一次暖意消息。新的 10 分钟档分身消息须与其语义区分，避免分身唠叨重复：

- 2.5h 那条 = "期待铺垫"（还早，先撩个氛围）。
- 10 分钟这条 = "马上见面"（临门一脚的提醒）。
- 文案分明，各自独立去重标记（2.5h 用其原有标记，10 分钟用 `reminder_10m_sent_at` 或分身侧单独标记），互不触发。

## 五、模块边界

- `apps/web/lib/appointment-time.ts` —— 纯函数时间工具，无副作用，可独立单测。被 4 个页面 + OrderCard 消费。
- `apps/api/src/jobs/appointment-reminder.ts` —— 单一职责：扫单 → 判档 → 推送/标记。依赖 `notifications.enqueue`、`realEpoch`、orders 表两列、分身消息触发。
- 迁移文件 —— 只加两列，无数据回填。

## 六、错误处理

- cron 单单失败不阻断整批（try/catch per order，记日志继续）。
- 推送失败由 `notifications`/`web-push` 现有 410/404 失活逻辑兜底，不在 cron 重试。
- 去重标记在推送 enqueue 成功后再写，避免推送失败却标记已发导致漏提醒（顺序：enqueue → 成功后 UPDATE）。
- 时区还原失败（技师 tz 缺失）退化为按 UTC 计算（与 v1 现状一致，不崩）。

## 七、测试

- `appointment-time.ts`：单测三个函数（今天/明天/跨周边界、倒计时分段、UTC→本地）。
- `appointment-reminder` cron：e2e 用真库造 LOCKED/PAID 订单于不同 minutesUntil 边界（61/60/11/10/1 分钟），断言：是否推送、推给谁、去重标记是否写入、二次扫不重复推。
- 边界：scheduled_at 为空 / 已过期 / IN_SERVICE 状态都不触发。
- 验证证据：cron 日志 + 通知表落库 + 推送 enqueue 调用（符合"完成必带 evidence"军纪）。

## 八、范围边界（YAGNI）

- 不做用户自定义提醒档位/开关（当前固定两档；用户已有 category 偏好可静默 `appointment_reminder`，够用）。
- 不另建 reminders 表（两档加列足够）。
- 不改 API 接口（scheduledAt 已返回）。
- 不动下单选时段逻辑（availability / scheduleOffer 不变）。
